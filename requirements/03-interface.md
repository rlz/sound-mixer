# 03. Interface

## Language

- English is the default interface language, including window text, error messages, and system permission descriptions.
- The HTML document declares English; the macOS app's development language is English.

## Icons

- The macOS Dock icon uses the same slider mark and sky-blue field as the in-app header, with rounded corners and optical margin matching neighboring macOS app icons.
- Use free Font Awesome SVG icons in the React interface through the official `@fortawesome/react-fontawesome` component. Import only used icons from `@fortawesome/free-*-svg-icons` packages so they are included in the local build and work offline.
- Prefer icon buttons for familiar actions when the icon is clear, to conserve space. Give every icon-only button an accessible English name and a visible tooltip or equivalent text on focus/hover when the action may not be obvious. Decorative icons are hidden from VoiceOver. Device unavailability and errors are not conveyed with an icon alone.

## Window

- Identify devices by Core Audio UID and virtual buses by UUID.

- The persistent top toolbar has an accessible Device settings button. Its shared dialog contains discovered physical-device visibility controls, the running-application catalog, and virtual-device creation. Newly discovered physical devices are visible by default. Hiding a physical device removes it from the main device panels while its routes and saved settings remain intact; the dialog always keeps it available to show again. Registering an application and creating a virtual bus happen in this dialog.
- The Device settings icon sits at the far right of the toolbar, after the master switch. Physical-device visibility uses colored eye and eye-slash icons with accessible action names. Application addition uses an icon button with an accessible name. Creating a virtual device leaves the dialog open and does not change the current destination selection. Registered applications and virtual devices have delete controls in both their cards and Device settings. Dialog deletion acts immediately; card deletion asks for confirmation. Removing an application unregisters it and removes its source rows from every mix; deleting a virtual bus follows the same reference validation as the card action.

- Keep the React interface split into focused modules: shared state types, native bridge, Zustand store, application composition, focused panels, dialogs, and reusable UI components. Components read shared state through narrow Zustand selectors and send native changes through the typed bridge; they do not access Core Audio. Keep transient interaction state (such as catalog search) inside the component that owns that interaction. Avoid passing full snapshots or long chains of callbacks through the component tree. Subscribe to per-item or per-panel state where practical so meter snapshots do not rerender unrelated UI.
- Zustand selectors must return stable values for an unchanged store snapshot. Apply fallback empty collections after subscribing so initial render cannot enter an update loop before the first native state arrives.

- The WebKit bridge accepts a versioned state snapshot from Swift and an allowlist of typed commands. The page sends a `ready` command after subscribing so the initial snapshot cannot be lost during startup. Every command includes a request ID and receives an accepted or rejected result. Swift validates required fields and ranges before saving; rejected commands leave saved state unchanged. Application gain commands accept only finite linear values from 0 through 10^(30/20); virtual Mix gain and Device volume commands accept only finite scalars from 0 through 1. Device volume and mute commands change Core Audio state without writing the mixer configuration and return a clear error when the device is unavailable or lacks the respective writable control. State snapshots combine discovered outputs with configured output mixes and buses. Audio graph application is added with the audio engine.
- The initial device screen is read-only. It lists only discovered devices with output channels and saved output mixes, and shows each item's name, UID, output channel count, and availability. A saved UID with no matching output remains visible as disconnected. Input-only devices are not listed as outputs.

- The main window uses the full available WebView area. A persistent toolbar sits above three edge-aligned work areas with fixed headings “Output,” “Mix,” and “Input”; only the content below each heading scrolls independently. The output and input areas have uninterrupted lists without type dividers. Order cards by type—system devices, virtual buses, then applications—and alphabetically by name within each type. The mix source list follows the same order. Keep names, availability, levels, and primary actions visible without requiring repeated navigation. Physical input and output availability appears as a colored dot immediately before the device name, without a visible status label; give the dot an accessible status name and hover tooltip. Keep capture progress and specific unavailability reasons in text. At the minimum supported window width, all three areas remain accessible.
- A compact footer stays fixed below the three work areas, outside their scroll regions. It shows the installed app's short version from the macOS bundle; the current pre-1.0 version is 0.9.0. The version is also available as accessible text.
- Prefer a dense layout with modest spacing and no redundant labels. Keep essential names, availability, values, and error explanations readable; use concise text and icon buttons for familiar actions to conserve space. Maintain keyboard and VoiceOver accessibility.
- Present input devices, output destinations, and mixes as consistent compact panels, not plain text lists. Input and output panels show live signal-level meters. Mix settings show live levels for the destination and its sources alongside their level controls. Each panel shows the item's name and state, plus icon-based management actions with accessible names. Keep state and error explanations understandable without relying on icons or color alone.
- Render meter values as peak amplitude from 0–1 full scale with a compact bar and a readable dBFS value. For visual position, allocate half the bar to −60…−12 dBFS and half to −12…0 dBFS so typical music peaks have room to move; 0 dBFS remains the right edge. Readings at or below −60 dBFS are shown as “No signal” with an empty bar, while unavailable or stale readings are “Inactive.” Keep the value on one line in a fixed-width, non-shrinking label so live readings do not reflow the panel. Keep the meter usable at larger system text sizes and expose its current value and inactive state to VoiceOver. Refresh from native runtime snapshots at up to 15 Hz; meter values are transient and are not saved.
- A muted source keeps its pre-mute input meter live. Mute and capture state are conveyed by the card controls, status indicator, and meter; do not add routine “Muted,” “Capturing,” “Available,” “Starting,” or “No signal” captions to cards. Keep actionable permission and startup errors visible.
- A selected destination's mix meter measures only Sound Mixer's rendered digital signal. The left physical-output card measures process audio sent to that particular device, including audio outside its Sound Mixer mix, and shows zero when the device reports mute or zero main volume. It must not mirror an application playing only through another device. A virtual bus card uses its mix meter because it has no separate device signal. Render configured virtual buses for metering even when no physical output consumes them; this meter-only rendering must not send audio to a device. A running tap with no recent audio buffers is an idle/no-signal state, not a capture error; show capture errors only for actual permission or startup failures.
- The app header contains the Sound Mixer name and a compact master switch showing On or Off, independently of the selected item. In the mix pane, show the selected destination name with its concise category (“System” or “Virtual”) beneath it; do not add “Output device settings” or a separate “Sources” heading. Virtual buses expose accessible rename and delete icon buttons beside the destination name. Rename opens a modal dialog and saves only after native confirmation; delete retains its confirmation warning.
- The full physical output and virtual bus card surfaces, including borders and padding, select that destination. Keep the pointer appearance consistent with the rest of the interface and allow card text selection; completing a text selection must not change the selected destination. Clicking an interactive control inside the card operates only that control and does not change selection.
- The wider left area lists system output destinations followed by virtual buses in one uninterrupted list. All discovered output devices appear whether or not a mix is configured. Input, output, and mix-input cards share one compact visual structure: a first line with an optional leading action, type caption, channel count, and optional trailing action; then a header with status indicator and name; a live level meter; and a shared mute/level-control row. Card-specific actions and editors are supplied as extensions to this shared structure. Status is gray while inactive, green while active, and yellow when a problem exists, with accessible status text. Each output device uses a compact card with its name, availability, live device signal meter, Core Audio device volume slider and value, and a separate mute button when the device exposes a writable mute control. Muting preserves the volume setting; unsupported controls are disabled with an accessible name and hover explanation; the card omits redundant Disconnected, Muted, and unavailable-control captions. Virtual bus cards also show their live destination signal meter and saved Mix gain slider with a dB value. Cards select an item, and selection is distinguishable without relying on color alone.
- Every virtual bus card in both the Inputs panel and destination panel exposes an accessible Delete action in its header. Confirm before deletion. Deleting a bus explains that existing use can prevent deletion.
- The Inputs panel lists discovered physical input devices, internal virtual buses, and registered application inputs in one uninterrupted list. Internal buses are labeled “Virtual” on their cards.
- When the interface first receives its state and no destination is selected, select the first available physical output; if none is available, select the first virtual bus. This gives mix-source actions a clear destination while preserving any selection the user makes.
- The center area shows the selected destination's settings and mix: name and type, availability, channel count, UID, route error, a live output signal-level meter for physical outputs, and compact source cards immediately after the destination information with per-source live signal-level meters and level controls. Do not show a duplicate mix-output summary or a second physical-output information card below the source cards. Add sources only through the right Inputs panel. Left-card Mix gain sliders apply changes during pointer or keyboard movement; intermediate updates are coalesced while a bridge command is in flight. On destination change, every slider immediately shows that destination's confirmed value and does not carry a prior destination's interaction state. Virtual item names are editable here; physical device names are read-only. Keep source rows compact and scannable.
- The right area lists every discovered system input device, saved input devices that are currently disconnected, internal virtual buses, and registered application inputs. Show each bus here with the concise “Virtual” category label, its name, live bus-output meter, and an icon-only Add to mix button with an accessible name and tooltip, using the same UUID-backed source as other mix controls. Do not add global mute or physical channel-routing controls to buses. Disable Add to mix if the bus is already in the selected mix or is the selected bus destination, and show a check icon for an already-added source. System inputs show availability, capture state, and live signal-level meters. Added applications show availability and capture state. A previously added application that is not running remains in the list as unavailable and resumes automatically when a matching process is available again. Do not populate this area with every running application by default: provide an add-application action that opens a separate searchable catalog of eligible applications. Each source row has an icon-only Add to mix button with an accessible name and tooltip. It is disabled when that source is already in the selected mix, and its enabled state updates whenever the selected destination changes based on that destination's mix. Remove sources from the mix in the selected destination's mix settings, not from the source panel.
- Each physical input device, internal bus, and added application has a global mute control and level control in the right area. Each mix source row has its own saved mute control, which silences only that row in the selected mix. Software gains display dB with 0 dB as unity and mute at the −60 dB endpoint; the global application input gain extends to +30 dB. Physical inputs and applications use source-level volume before per-mix row gain and routing. Muting a source in the Inputs area remains global; muting a mix row does not change the source's global state. Mute and source-level volume are saved and restored.
- Selecting an output opens its settings in the center area. Selecting a virtual bus opens its settings there; its saved name is edited there and persisted after native confirmation. Muting does not stop capture, so an actively captured muted input can continue to show its input level.
- After creating a virtual bus, select it and open its mix settings in the center area as soon as the updated native state arrives.
- All software gain controls show dB values in 0.5 dB steps: −60 dB is mute, 0 dB is unity, and positive values include a plus sign. Global application input gain ranges through +30 dB; per-mix rows, channel gains, and virtual destination gains stop at 0 dB. Application gain affects that application in every mix; the Inputs meter stays pre-gain, while mix-row and destination meters reflect the boost. The engine limits the final output to full scale, so sustained boost into the limiter can distort.
- Physical output cards show Device volume from 0% to 100% using the live Core Audio main-volume scalar. The controls work even before a mix is configured and while mixing is off, reflect changes made outside Sound Mixer, and show the current device value after native confirmation. When the output exposes a writable mute control, its separate button toggles mute without changing the current volume. Setting volume to 0% also enables mute; setting it above 0% disables mute. During pointer movement, send the first device-volume change immediately, then apply the latest value after each Core Audio write completes; keep the control responsive throughout. A disconnected output card is dimmed with a gray availability dot, no error message, and disabled volume and mute controls; it remains selectable so its saved mix can be managed. Show a Delete mix button on disconnected output cards and in the selected disconnected output's Mix panel. Confirm deletion and remove only that output's saved mix. A connected device without a readable and writable main control shows a disabled volume control and a tooltip explanation, without falling back to digital Mix gain. Sound Mixer restores the previous device volume and mute state on normal exit when each still has its last app-set value. Physical mix output stays at unity.
- Virtual bus cards in the left area show saved software Mix gain in dB, from mute at −60 dB through 0 dB (unity). Their right-area level controls are the same setting and reflect confirmed updates from either panel. Their mute controls in both panels share the same saved mute state. Software gains never change Core Audio device volume. Device volume remains in percent; software gains use dB in all cards and editors.
- Every interface dialog uses the shared dialog shell with a fixed title bar, an accessible close icon button, and a separately scrollable body. Dialogs close by the close button, Escape, or backdrop click.
- The channel count in every selected-mix source card is a keyboard-accessible button. It opens a wide modal titled `Chanel Routing`, with source channels as rows and destination-mix channels as columns. Each cell is a compact square toggle with a 1 px gap, an accessible input/output label, and pressed state; several output cells in a row may be selected. Output columns are grouped beneath the shared `Out` heading, aligned to the first output column, and numbered individually. The modal body supports scrolling for large devices while its title remains fixed; horizontal scrolling reaches the dialog body's edges, with content inset inside the scroll area and 32 px of space between the matrix and the scrollbar. The scroll area extends to the bottom of the dialog body. Each physical input or application channel row starts with its channel number, followed by a live meter and independently labeled gain slider on separate lines; the meter spans the available row width. Routing and gain edits are saved per row and per destination; the modal reflects confirmed native state. The former `Mono placement` control and inline four-choice physical-channel selector are removed.
- Bus renaming uses an in-interface dialog so name entry works consistently in WKWebView. Bus creation does not require name entry.
- Deleting a virtual bus that is still used as a source by another mix is rejected with a validation error; remove those source rows first. Bus names are trimmed, must be non-empty, and are limited to 64 characters.
- The center add-source picker and right-side Inputs panel expose the same internal buses as mix sources. Applications are added explicitly from the searchable application catalog opened from Inputs; the catalog lists eligible currently running applications not already registered, searches names and bundle identifiers, and does not add them merely by browsing. Existing registered applications remain in Inputs when their process is unavailable.
- When adding a source, unavailable items include a reason. The catalog does not offer a new row for a missing input device.
- An existing input stays in its mix row when its device is missing, including at launch. It is shown unavailable and can be explicitly removed from the mix. The interface does not offer to create a new row for a missing device, and device absence never removes a source row automatically.
- A disconnected physical input in a mix is shown as a dimmed card with a gray availability dot labeled Disconnected for accessibility. It has no error message or yellow problem indicator. Its meter is inactive, its mute, gain, and channel-routing controls are disabled, and only Remove remains active and undimmed. Removing it from any card removes its source row from every output and virtual bus mix, and clears its saved global mute and gain. Confirm deletion. Reconnecting the same UID restores the controls and live state while it remains configured.
- A disconnected physical input in the Inputs panel is also dimmed with a gray availability dot and no error message. Its meter is inactive, Add to mix is replaced by a Delete button, and its mute and gain controls are disabled. Confirm deletion. Reconnecting the same UID restores the controls and live state while it remains configured.
- The matrix is available for every connected mix source. Application taps expose two source rows; virtual buses expose their configured 1–16 source rows; physical devices expose their reported channel count. Saved physical input routing remains intact while a device is disconnected and is available again when it reconnects. The columns follow the selected destination: all physical output channels or the selected bus's configured 1–16 channels.
- Device settings show each virtual bus channel count with a 1–16 selector and accessible increment/decrement buttons. Changes save immediately and update routing editors and dependent audio renderers.

## States and feedback

- When invalid saved settings are discarded at startup, show a dismissible notification over the interface; close it automatically after five seconds. If the configuration file cannot be removed, keep the actionable startup error visible.
- An empty mix explains how to add a source.
- A destination has editable mix settings without a separately created mix object. An output mix is saved only while it has settings; removing its last source makes it equivalent to no mix. Bus mix values at their defaults with no sources are likewise treated as absent. The mix editor always remains available for the selected destination. Its top Reset button clears its sources and restores default gain; for a physical output this removes the saved output mix, while buses remain and only their mix settings reset.
- Microphone or system-audio permission denial appears beside the affected source and provides an action to open System Settings.
- Source rows show capture progress, active capture, permission denial, or the native unavailable reason. A denied source provides a validated bridge action that opens the relevant macOS privacy settings pane.
- Missing output devices and channel incompatibilities are shown in the selected device state.
- A route validation error identifies affected items and does not change the active audio graph.
- Level and name changes appear after successful confirmation from Swift. On failure, the UI restores the confirmed value and shows the reason.
- While mixing is off, sliders and mix contents remain visible and editable; the master switch communicates its Off state.
- Swift state snapshots combine saved items and discovered devices, reporting availability and each capture or output stop reason separately. After a missing device is connected or removed, the interface updates from a confirmed snapshot without restarting the window.

## Accessibility

- All actions are keyboard accessible; sliders have text labels and numeric values. Static interface text, including labels inside selection buttons, can be selected and copied with the standard macOS Copy and Select All commands.
- Level sliders keep their in-progress value stable while native state snapshots arrive. Software gain sliders, including per-channel gains in the routing dialog, stay enabled and follow pointer movement while native writes are in flight; intermediate changes are coalesced and the latest value is applied. Keyboard adjustments commit on key release. Reconcile the displayed value with confirmed native state after interaction; rejected edits return to the last confirmed value. After interaction and any in-flight write finish, an external Core Audio volume change updates both the numeric value and slider thumb, even if a prior device readback differed slightly from the requested value.
- Respect the macOS system text size, contrast, and dark mode.
- Expose the physical-device availability dot as accessible text and a tooltip; keep capture state and device errors visible in text.
- Application inputs are explicitly registered from the searchable catalog and exist independently of destination mixes. Registration immediately starts capture while Mixing is On and displays a live pre-gain meter. Their status indicator reflects the process-tap capture state (green while capturing, gray while idle or stopped, yellow on an error). Registered applications can be added to and removed from mixes like any other input; removing the last mix row leaves the input registered. The catalog lists eligible running applications that are not registered.
